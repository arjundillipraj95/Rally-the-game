# P0.10 Server hosting: can Rally battles run on a server?

Short answer: **yes**. The battle code runs on a server as it is. The cheapest start is a
Cloudflare Durable Object (DO) on the free plan, which we already use. India is the open question:
Cloudflare has no DO site in India, so India battles would run in Singapore. Test that ping from a
Jio/Airtel phone before building it.

## 1. Proof: the battle runs without a phone

`game/store/p010_headless.mjs` runs one Crown battle on the mountain in plain Node. It loads only
`core/sim.js`, `state.js`, `world.js`, `nav.js` and `config.js`, with no three.js, no DOM and no
browser, and runs the full 10 minutes at 30 steps a second. Every captain is a computer captain,
which is the heaviest case. It ran on this shared 2-core box with `nice`.

| Battle | Soldiers (avg / peak) | CPU per game second | Per step | Memory | Snapshot (median / max) |
|---|---|---|---|---|---|
| Trio, 12 captains | 136 / 167 | **133 ms** (13% of one core) | 4.4 ms | 37 MB | 4.7 KB / 5.5 KB |
| Solo, 4 captains | 86 / 109 | **65 ms** (6.5%) | 2.2 ms | 13 MB | 3.4 KB / 4.2 KB |

- One core can run about **7 Trio battles at once** (plan for 5).
- The snapshot is our real `encodeSnap`, copied from `net/netgame.js` as text, so the game itself
  is unchanged. The host already trims any snapshot over 3.9 KB, so in practice it sends about
  **3.9 KB at ~12 a second, which is ~48 KB/s for each player**.
- The core needs no split. It has no imports from three.js, the DOM or Node, so it can be bundled
  into a Worker as it is.
- What does need a split is the host side of `net/netgame.js`. `encodeSnap` and
  `netHostReadInputs` use only core code and `session.NET`, but the file also imports UI and
  three.js modules (`ui/audio`, `ui/hud`, `ui/input`, `render/effects`, `render/camera`,
  `ui/timeline`). Moving those two functions into a new UI-free `net/hostcore.js` is about half a
  day's work.

**Why this matters for the 400 ms ping.** Today the host phone sends 11 copies of every snapshot,
about 0.5 MB/s (4 Mbit/s) of upload over mobile data. That is a likely cause of the queueing and
the 400s. A server sends each phone only its own copy.

Jio/Airtel traffic to free Cloudflare sites is
[served from Singapore or even Amsterdam](https://hn.jakechampion.name/reader/https://punits.dev/blog/cloudflare-latency-india).

**Cost by daily players.** Assumptions: 2 matches a day each, 10 players a match, 10 minutes a
match, phones sending input 15 times a second (as now), and about 0.35 GB of traffic out per match.

| Daily players | Matches/day | Battles at once (peak) | Cloudflare DO | Oracle free | Vultr (Mumbai + US) |
|---|---|---|---|---|---|
| 100 | 20 | ~1 | **$0** (free plan holds about 18 matches/day; $5 if over) | $0 | ~$10/month |
| 1,000 | 200 | ~5 | **~$11/month** | $0 (fits in 2 cores, 2 TB) | ~$12-20/month |
| 10,000 | 2,000 | ~50 | **~$106/month** (≈$49 requests + $53 run time) | outgrows it (~8 cores, 20 TB) | ~$80-150/month |

How the DO figures work: each match is about 5,400 billed requests (incoming messages count 1 per
20) and 77 GB-s (128 MB for 600 s). Outgoing messages are free, so the bandwidth costs nothing.
Requests are what run out first on the free plan.

## 3. Recommendation

1. **First, P0.10b ping probe (S, about 1 day, $0).** Add a tiny "ping" DO with an `apac` hint
   next to `Hub`. Measure from Indian phones (Jio and Airtel) and from the US. If India gets under
   ~120 ms, use Cloudflare. If not, India battles go on a Vultr Mumbai box ($5/month, Node, same
   code). Either way the $50 lasts many months.
2. **Server battles (O, about 1 week).**
   - Split `net/hostcore.js` out of `netgame.js`.
   - Add a `Battle` DO that runs `startMatch`/`update` 30 times a second and keeps the
     `presence()` message format.
   - Switch the client from PeerJS to a WebSocket with the same `presence/peers/onPeers` shape as
     `p2p.js`.
   - `Hub` creates the battle in the right region (needs P0.11).
   - Keep peer-to-peer as a fallback while this is tested.
3. **Phase 0 changes.**
   - P0.9 host hand-over: **drop**, since the server never leaves.
   - P0.4 best host: **drop**.
   - P0.8 fair timing: **mostly drop**. No player has a zero-ping host any more. Keep the parry
     allowance for remote players.
   - P0.11 region matchmaking: **needed first**.
   - P0.7/P0.7b smoothing: **keep**.
   - P0.5 Cloudflare TURN: **drop**. Game traffic over a WebSocket gets through every network.
4. **Voice.** V1 stays phone-to-phone, so phones that can't link directly still need a TURN relay
   (V1b, the Metered free tier). Sending voice through our server would cost far more traffic than
   the battle itself.

Risks:
- India's path to Cloudflare (step 1 tests it).
- The free-plan CPU rule for a DO game loop (also tested in step 1).
- Mixed India-US matches stay at about 250 ms whatever we do.
- The phone still decides where its own captain is (we send `cap`). That is fine for now, but it
  could be used to cheat later.
